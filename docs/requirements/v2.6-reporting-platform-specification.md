# v2.6 Reporting Platform — Consolidated Specification

> Authoritative consolidation of the nine approved requirements batches for the v2.6
> reporting platform. Base: deployed v2.5.0 (tag `v2.5.0` @ `39674ed`, ledger 34, 89 tables).
> Branch: `feat/v2.6-reporting-platform`. All UI is Arabic RTL; this document is
> developer-facing and therefore in English per the language policy (Arabic strings quoted
> inline where they are the product).

## 0. Relationship to v2.5.0

v2.5.0 delivered the reporting *engine*: a unified filter framework
(`src/lib/reports/filters.ts`), a domain-organised report catalogue, the report builder
authoring surface (`/reports/builder`), saved report *settings* templates
(`report_templates`, migrations 0032/0033), the individual-report workflow, and
filter-consistent PDF/CSV/XLSX/DOCX exports through the issuance pipeline.

v2.6 turns that engine into a reporting *platform*: persistent report instances with a
lifecycle (draft → final → archived), true immutable snapshots, a formal identity/template
system, a full export suite (DOCX/PDF/XLSX/ZIP) with RTL page design, asynchronous
generation, an archive with search and signed-copy upload, and CI that proves all of it
with synthetic data.

Nothing in v2.6 removes or reintroduces behaviour the principal rejected in earlier
rounds. Approved v2.5.0 behaviour is preserved unless this specification explicitly
changes it.

## A. Report builder

- Arabic-first, fully RTL report builder extending `/reports/builder`.
- Selectable: report type (from the existing catalogue), period, scope, filters, sections,
  metrics, tables, charts, evidence, attachments, template, and output formats.
- Live preview updated by filters; preview target ≈ 3 s.
- «إعادة تعيين المرشحات» reset-filters action.
- Empty fields and sections are hidden automatically, with an explicit option to show them
  («إظهار الحقول الفارغة»).
- Names and numbers in the *application* preview are interactive links to their source
  detail pages (links are an app-preview affordance only; exports carry plain text).
- Sections can be reordered where the report type supports it.
- Reusable report *settings* can be saved (existing `report_templates`) — settings only,
  never report data.
- «نسخ من تقرير سابق»: a previous report instance can be copied as a starting point for a
  new draft.
- Pre-export validation produces clear warnings; warnings are non-blocking unless
  correctness or safety is affected.
- Report statuses: **DRAFT** («مسودة»), **FINAL** («نهائي»), **ARCHIVED** («مؤرشف»).
  - Only drafts may be deleted.
  - Final reports can never be edited or deleted.
  - A "new version" of a final report creates a **new report** with a **new number** and a
    reference to the original.
  - The report number is assigned **only at finalization**.
  - Finalization is **transactional and idempotent** (double-submit cannot assign two
    numbers or duplicate outputs).

## B. Immutable snapshots and archive

- A final report is a true immutable snapshot: later changes to source data never change
  it.
- The snapshot preserves: the exact selected scope, filters, sections, rendered data,
  metadata, template + template version, attachment/evidence references, and the generated
  outputs needed for reproducibility.
- Generated Word/PDF/Excel/ZIP files, the uploaded signed copy, and used attachments are
  preserved as stored files referenced by the report instance.
- A signed copy can be uploaded after external signature («نسخة موقعة»).
- The archive is searchable (title, number, type, period, status, date range).
- Archiving changes only the lifecycle state — never the immutable content.
- Accidental mutation is prevented in application code, server actions, background jobs,
  cascades, and migrations; regression tests prove snapshot immutability.

## C. Domain coverage

Detailed, filtered, cross-domain reporting for:

- programs and initiatives; weekly follow-up and execution status; program owners; domains
- evidence counts and evidence readiness; delayed and incomplete programs
- performance forms; teachers and employees; detailed and statistical performance
  analysis; low performers
- committees, members, assigned work, and signatures
- maintenance; school building and building-sketch information
- budget, spending, and remaining amounts
- executive summary; periodic reports; end-of-term/final reports
- infographic-style reports where already supported

Filters must be broad enough for each domain and must **never leak records outside the
selected scope** — including related records of included records.

## D. Privacy and data minimization

- Only data required by the selected report is shown.
- National ID and contact information are hidden by default; explicit opt-in per report
  where legitimately needed.
- No data outside the selected filters/scope, even when related to included records.
- Authorization and filter boundaries are tested.
- Filenames and user-controlled text are sanitized.
- Spreadsheet formula injection is prevented; unsafe HTML/content injection in previews
  and exports is prevented.

## E. Identity and templates

- Formal school identity aligned with Ministry of Education presentation conventions,
  without claiming reports are issued by the Ministry itself.
- «إدارة التعليم» is used everywhere applicable. «مكتب التعليم» is removed from identity
  settings, school metadata, templates, reports, letters, fields, filters, generated
  filenames, and display labels.
- Base templates (system-protected, cannot be deleted or destructively modified;
  customized copies allowed; no unrestricted general-purpose template designer):
  1. official report submitted to إدارة التعليم
  2. internal administrative
  3. concise executive
  4. detailed analytical
  5. identity-free initial print
- Central identity settings: school/complex name, logo, إدارة التعليم, contact
  information, principal's name, identity colors, editable header, editable footer.
- Per-report identity overrides never change global settings.
- A default template per report type; another template selectable at creation.

## F. RTL, page design, and printing

- Fully RTL Arabic reports: tables, numbers, headings, charts, headers, footers.
- Mixed Arabic/English/dates/reference numbers keep correct bidirectional order.
- Page support: A4 portrait, A4 landscape, automatic orientation by content, and mixed
  portrait+landscape sections within one Word document.
- Formal reports may contain: cover, report title, school, period, report number, issue
  date, table of contents where needed, page numbers, editable header/footer, optional
  approval box.
- Cover and TOC are automatically omitted for short reports unless explicitly enabled.
- Prevented: blank pages, orphan headings, broken table rows, corrupted pagination,
  detached headers.
- Wide tables handled automatically: intelligent landscape conversion, controlled
  scaling, splitting where necessary, repeated table headers.
- Real paginated print preview matching the exported PDF as closely as technically
  practical.
- Charts show labels/values and never rely on color alone; calm official colors readable
  in grayscale.
- Optional generated list of attachments and evidence used.

## G. Exports

**DOCX** — fully editable; correct RTL; stable tables/layout; editable header/footer;
mixed page orientations; tested in real Microsoft Word before final acceptance.

**PDF** — fixed final representation matching the approved preview; embedded/available
Arabic fonts; no clipped Arabic, missing glyphs, or broken charts.

**XLSX** — summary sheet + raw-data sheet; structured tables; filters; charts where
useful; extraction date/time; explicit description of filters used; safe valid worksheet
names; formula-injection protection; RTL sheet presentation where supported.

**ZIP** — all selected outputs + signed copy + relevant attachments; path-traversal
prevention; deterministic safe names; verified integrity.

**Filename format** — «الاسم الكامل للتقرير - تاريخ إنشاء التقرير» (full report name and
generation date, never abbreviated codes).

## H. Attachments and security

Uploads validated by: allowed type, real file signature/content where practical,
extension, size, sanitized name, executable/dangerous-file rejection. No administrative
attachment-count limit, but safe technical limits prevent denial of service. No sensitive
filesystem paths or stack traces exposed to the UI.

## I. Background generation and reliability

- Large reports generate asynchronously without freezing the page.
- Understandable progress/status; useful failure reason and a «إعادة المحاولة» retry.
- Draft preserved on generation failure. Jobs and retries idempotent; re-export never
  duplicates records or attachments; worker interruption/restart tolerated.
- No races around finalization, attachment persistence, storage, or revalidation.
- D-053 stands: no `revalidatePath`/post-commit invalidation may abort a successful
  Server Action response.

## J. Performance targets

- Normal report pages ≈ 2 s under representative local conditions; preview updates ≈ 3 s.
- Large generation runs in the background without blocking ordinary use.
- No N+1 access, no unbounded in-memory processing; measurable validation scripts.

## K. Users and permissions

- Principal remains the only active user model. Architecture stays capable of future
  granular permissions without activating a role matrix now. No comprehensive audit log,
  no separate export-history feature — only operational metadata necessary for report
  correctness, state, retries, and preserved outputs.

## L. Quality gate

Tested with: small/medium/large datasets; images; long Arabic tables; empty and partially
empty reports; mixed Arabic/English; Hijri and Gregorian dates; all base templates; Word,
PDF, Excel, ZIP, preview, and print; snapshot immutability; filter isolation; final-report
immutability; delete restrictions; retry/idempotency; attachment validation;
upgrade/migration behaviour; rollback compatibility.

Real-Microsoft-Word acceptance is explicitly tracked; if it cannot genuinely be performed
in the available infrastructure, the RC report says so.

**Release blockers:** data outside filters; mutable final snapshots; PDF/preview
mismatches that change meaning; corrupted DOCX/XLSX/ZIP; broken RTL; lost attachments;
unsafe uploads; migration/data loss; failing tests; unstable numbering/finalization.

## L2. Amendments after the independent RC review (2026-08-08)

The review found the first RC report overstated completeness. The specification itself is
unchanged — these are clarifications of how approved items are satisfied, recorded so the
next reader can check them:

- **Release identity** is `2.6.0` in `package.json`, the lockfile and `RELEASE_VERSION`;
  `/api/health` and the in-app version marker report it (pinned by `release.test.ts` and
  `discoverability.test.ts`).
- **§A builder** is satisfied by `/reports/builder` itself, not a second surface (D-064):
  it saves reports and edits them via `instance=<id>`; selected output formats are stored
  on the report and are exactly what generation produces; evidence/attachment selection
  uses the platform's one evidence register; saved report settings open in the builder.
- **§A finalization** carries an optimistic lock on the draft revision (D-061).
- **§B/§G package** is never downloadable stale, and rebuilds run as recorded jobs (D-062);
  integrity is checked against bytes on disk (D-063); migration 0036 narrows what a ZIP
  row may change.
- **§E templates** have a full lifecycle: copy from a base, edit, archive, restore, with a
  configurable default per report type — and still no free-form HTML/CSS designer (D-058).
- **§E identity** includes central contact information with per-report override.

## M. Out of scope (explicit)

- Deployment to port 3080, production database changes, release tag, PR merge — all
  require separate explicit authorization from the owner.
- Unrestricted template designer; full role matrix; comprehensive audit log; export
  history feature; concepts removed or rejected in earlier releases.
